## 1. 确定性是第一原则

格斗游戏的网络同步建立在"两台机器用相同输入算出的结果必须逐帧一致"这个前提上。任何不确定性（随机数、浮点精度差异、未排序的集合遍历）都会导致状态分歧，积累后表现为"我看到我打中了你，你看到你防住了"。

Fyren 从四个层面保证确定性：

### 1.1 输入排序

`GameWorld.java:59`：
```java
inputs.sort(Comparator.comparingInt(c -> c.playerId));
```
同一帧 P1 和 P2 同时出招，谁先处理？如果两台机器各自按"收到的顺序"处理，结果不同。按 `playerId` 排序 → 顺序固定 → 结果一致。

### 1.2 禁止随机数

整个 `game/` 包没有 `Math.random()` 或 `Random` 类。所有"变化"来源只有玩家输入，而输入是确定的 boolean 数组。

### 1.3 全整数或可控浮点

位置用 `float`，但 Java `strictfp` 关键字确保同一 JVM 版本的浮点运算结果一致。格斗游戏的核心状态（血量、帧计数、硬直时间）全部是 `int`。

### 1.4 禁依赖外部状态

`System.currentTimeMillis()` 只在网络层（FrameSyncManager）使用——帧同步用固定时间步长（16.67ms），不依赖实际经过的时间。`GameWorld.update()` 不读系统时钟。

## 2. Fighter 动作状态机

`Fighter.java:26-31` — 状态机核心：

```java
public enum ActionState { IDLE, STARTUP, ACTIVE, RECOVERY, STUN, DASH }
public enum ActionType { NONE, PUNCH, KICK, THROW, SPECIAL }
```

### 状态转换图

```
                   ┌─────────────┐
         出招      │   STARTUP   │  前摇结束
    IDLE ────────→ │  (前摇帧)    │ ─────────→ ACTIVE (判定帧)
     ↑             └─────────────┘              │
     │                                          │ 判定结束
     │            ┌─────────────┐               ↓
     │            │   RECOVERY  │ ←─────────────┘
     │            │  (后摇帧)    │
     │            └──────┬──────┘
     │                   │ 后摇结束（或影取消）
     │ 硬直结束          ↓
     └────── STUN ←──── 任意状态可被打断
              (僵直帧)
```

### 帧数据表

`Fighter.java:64-69`：
```java
// [前摇帧, 判定帧, 后摇帧]
private static final int[] PUNCH_FRAMES  = {3, 3, 5};   // 3帧起手 + 3帧判定 + 5帧收招 = 11帧总长
private static final int[] KICK_FRAMES   = {5, 3, 7};   // 更慢但伤害+2
private static final int[] THROW_FRAMES  = {4, 2, 6};   // 破防
```

**为什么不同动作有不同的帧数据？** 这是格斗游戏的核心设计空间：
- 拳：快（11 帧）但伤害低，适合确认和压制
- 脚：慢（15 帧）但伤害 +2，高风险高回报
- 投技：破防，对手不能格挡
- 特殊技：每个角色不同帧数据（差异化）

### 状态转换代码

`Fighter.java:203-226` — `updateAction()`：
```java
actionTimer--;
if (actionTimer <= 0) {
    if (actionState == STARTUP) {
        actionState = ACTIVE;       // 进入判定帧
        actionTimer = frames[1];
        isAttacking = true;         // 碰撞系统用这个判断
    } else if (actionState == ACTIVE) {
        // 影取消：KAGE 特殊技跳过 RECOVERY

            actionState = IDLE;     // 直接回 IDLE

        actionTimer = frames[2];
    } else {
        actionState = IDLE;         // 收招结束
    }
}
```

## 3. 碰撞系统 — 帧数据感知

`CollisionSystem.java:16-42` — `checkCollisions()` 核心逻辑：

```java
boolean p1Attacking = p1.isAttacking() && a1.width > 0 && a1.height > 0;
boolean p2Attacking = p2.isAttacking() && a2.width > 0 && a2.height > 0;

boolean p1HitsP2 = p1Attacking && a1.intersects(h2);  // P1攻击框 ∩ P2受击框
boolean p2HitsP1 = p2Attacking && a2.intersects(h1);

// 关键判断顺序：相杀优先于单方面命中
if (p1HitsP2 && p2HitsP1) {
    handleClash(p1, p2);    // 相杀：各受半伤 + 3帧短僵直
} else {
    if (p1HitsP2) applyHit(p1, p2);
    if (p2HitsP1) applyHit(p2, p1);
}
```

### 三种命中场景

**① 普通命中 — `applyHit()`（第 67-93 行）**：
```java
int baseDmg = calculateDamage(attacker);
boolean isThrow = attacker.getActionType() == THROW;
// 投技破防：全额伤害
// 防御格挡：伤害减半
defender.takeDamage(baseDmg, isThrow);
// 特殊技附加效果
// 武·气合掌 → 击退对手 50px
// 影·影袭   → 自身突进 60px
```

**② 相杀 — `handleClash()`（第 97-115 行）**：
- 双方同时处于判定帧且攻击框相交
- 各受对方伤害的一半
- 各受 3 帧短硬直（`applyShortStun()`）
- 不会触发格挡判定

**③ 角色分离 — `resolveOverlap()`（第 117-134 行）**：
- 受击框重叠时各推开 overlap/2
- 防止两个角色视觉上重叠

### 伤害计算（第 45-65 行）

```java

    case KICK:  dmg += 2; break;
```

## 4. 三角色差异化设计

`Fighter.java:56-61` — 特殊资源系统：

| 角色 | 资源机制 | 就绪条件 | 消耗 |
|------|---------|---------|------|
| 影 (KAGE) | 3 秒 CD | `specialCooldownRemaining <= 0` | CD 重置为 180 帧 |
| 武 (TAKESHI) | 输出充能 | `damageDealtSinceLastSpecial >= 40` | 充能归零 |
| 刚 (GOU) | 承伤充能 | `damageTakenSinceLastSpecial >= 50` | 充能归零 |

影的额外特性：特殊技可**取消收招**（`updateAction()` 中 `actionState = IDLE`），意味着可以在连段中提前取消动作，形成压制链。这是格斗游戏中"取消技"的标准实现。

### 冲刺系统

**择边博弈**：冲刺可以向前或向后 → 可以择边（cross-up）→ 对手需要判断防御方向 → 这就是格斗游戏的核心博弈。

## 5. GameWorld 的确定性更新循环

`GameWorld.java:47-75`：
```java
public void update(List<InputCommand> inputs, int frameNumber) {
    this.currentFrame = frameNumber;
    timerFrames--;  // 99 秒倒计时

    inputs.sort(Comparator.comparingInt(c -> c.playerId));  // ① 确定顺序

    for (InputCommand cmd : inputs) {
        if (cmd.playerId == player1.getId()) player1.update(cmd, this);
        else if (cmd.playerId == player2.getId()) player2.update(cmd, this);
    }

    collisionSystem.checkCollisions(player1, player2);  // ② 碰撞检测
    checkDeath();                                        // ③ 死亡判定

    if (currentFrame % 10 == 0) saveSnapshot();          // ④ 每10帧存档
}
```

### 超时判定

```java
private void endGameByTimeout() {
    gameOver = true;
    if (hp1 > hp2) winnerId = 1;
    else if (hp2 > hp1) winnerId = 2;
    else winnerId = 0;  // 平局
}
```

血量百分比 → 判定胜负。这点比"剩余血量绝对值"更公平。

## 6. 受击框与攻击框（可视化）

`Fighter.java:386-437` — `getHitbox()` 和 `getAttackBox()`：

- **受击框**：基于 `FighterPreset` 的宽高，不同角色不同
- **攻击框**：仅在 `ACTIVE` 状态返回有效矩形，尺寸和位置随动作类型变化

例如冲拳的攻击框 = 角色前方 50px 宽 × 30px 高的矩形，而刚的特殊技 = 80px 宽的巨大水平攻击。训练模式用 ShapeRenderer 绘制绿色受击框 + 红色攻击框。

## 7. 面试追问 & 标准回答

### Q: 为什么不用物理引擎（Box2D 等）做碰撞？

> 格斗游戏的碰撞不是物理碰撞，是**帧数据碰撞**。两个角色不会互相推挤（除了分离逻辑），攻击判定依赖于"攻击方是否在判定帧"而非"两个碰撞体是否重叠"。物理引擎解决的是"两个物体相撞后的速度和位置"，而格斗游戏需要的是"第 N 帧的 10px × 20px 矩形是否与对手的受击框重叠"——逻辑完全不同。

### Q: 如果两台机器帧率不同怎么办？

> `FrameSyncManager` 使用固定时间步长（16.67ms = 60fps）。无论显示器刷新率是多少，游戏逻辑总是以 60fps 推进。渲染帧率可以更高或更低（通过 delta 累积追赶），但逻辑帧率恒定。

### Q: 相杀（clash）和同时命中的区别是什么？

> "同时命中"是网络现象——两台机器各自判定命中。相杀是**设计上的机制**——同一逻辑帧内双方都在判定阶段且攻击框相交时，故意让双方各受半伤而非随机选一人获胜。这是确定性的体现：两台机器对"是否相杀"的判断必定一致。

### Q: 为什么角色的帧数据是硬编码数组而不是配置文件？

> 这是个人项目的合理取舍。配置文件（JSON/YAML）需要解析器、错误处理、热重载，增加了工程复杂度。对于 3 个角色 × 4 种攻击的动作数据，硬编码在源码中足够。如果扩展到 20 个角色，就会引入数据驱动设计。面试时坦诚说明这个取舍比吹嘘"支持配置化"更好。

### Q: Fighter 里为什么既存 `lastRawDamageReceived` 又区分原始伤害和实际伤害？

> 原始伤害用于 `onDamageDealt()` 累加（武的资源充能），实际伤害用于扣血。如果格挡减半后按实际伤害充能，武在面对格挡时会更难积攒资源——设计意图是鼓励进攻，所以用原始伤害充能。
