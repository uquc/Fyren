# 第一讲：帧同步与回滚网络

> 源码文件：`FrameSyncManager.java`、`GwtFrameSyncManager.java`、`InputBuffer.java`、`InputCommand.java`、`GameStateSnapshot.java`、`GameWorld.java`

---

## 1. 要解决什么问题

两个玩家隔着网络对战。P1 在北京按了一拳，这个"按拳"的信息要经过 30-50ms 才能到达 P2 的电脑。

**最笨的方案（悲观锁步）**：P1 输入 → 发给服务器 → 服务器等 P2 输入也到了 → 一起算一帧 → 发给双方。问题：每个人都要等最慢的那个人，延迟 = 两人网络延迟之和，卡顿感极强。

**Fyren 的方案（乐观帧锁定 + 回滚）**：
- P1 不等 P2 的输入，直接用**上一帧的输入预测**当前帧 P2 会做什么
- 万一预测错了（P2 实际输入和预测不同），**回滚**到出错的那一帧，用正确的输入重新模拟

核心思想：**宁可算错再改，也不等。**

## 2. 数据结构：从底层往上讲

### InputCommand — 最小编码单元

`InputCommand.java:6-18` — 每帧每个玩家产生一条。9 个 boolean：

```java
public int frameNumber;     // 属于第几帧
public int playerId;        // 谁的操作
public boolean up, down, left, right;  // 方向
public boolean punch, kick, special;    // 拳/脚/特殊技
public boolean dashForward, dashBackward; // 冲刺
```

**为什么全是 boolean？** boolean 在网络上序列化不会产生精度问题。两台机器对 `true/false` 的理解永远一致。如果用 `float` 表示方向强度，不同 CPU 架构的浮点舍入可能产生分歧。

`equals()` 方法（第 31-41 行）比较全部 9 个字段——这是回滚检测的核心：当远程输入到达时，用它和本地的预测输入做 `equals()`，不同就触发回滚。

### InputBuffer — 历史记录

`InputBuffer.java:9-15`：

```java
private final Map<Integer, InputCommand> inputs = new HashMap<>();
private int currentFrame = 0;  // 已确认到达的最高帧号
```

本质就是一个 `HashMap<帧号, InputCommand>`。关键方法：

| 方法 | 作用 |
|------|------|
| `addInput(cmd)` | 存入，同时更新 `currentFrame = max(currentFrame, cmd.frameNumber)` |
| `getInput(frameNumber)` | 按帧号取，没有就返回 `null` |
| `rollbackTo(frameNumber)` | 删掉该帧之后的所有记录 |

**`currentFrame` 的语义**：这个缓冲区里最新的帧号是多少，**不是**"游戏进行到第几帧"。`FrameSyncManager` 用这个值来判断"远程输入到齐了没有"。

### GameStateSnapshot — 回滚的"存档点"

`GameStateSnapshot.java:7-73` — 每 10 帧拍一次照。**40 个字段**，覆盖双方角色的全部状态：

```
每个角色 20 个字段：
  x, y, vx, vy               — 位置和速度
  health                      — 血量
  actionState, actionType, actionTimer — 动作状态机三要素
  blocking, dashing           — 防御/冲刺
  stunRemaining               — 硬直剩余帧
  dashCharges, dashRechargeTimer, dashDirection, dashTimer — 冲刺系统
  specialCD                   — 特殊技CD（影）
  damageDealt                 — 累计造成伤害（武）
  damageTaken                 — 累计受到伤害（刚）
  facingRight                 — 面朝方向

+ 世界状态：
  timerFrames, gameOver, winnerId
```

`restore()` 方法（第 76-101 行）逐字段写回 `Fighter` 对象。**快照的本质不是"回退"，而是"用存档覆盖当前状态，然后从存档点重新模拟到当前帧"。**

## 3. 核心循环：`gameLoop()`

`FrameSyncManager.java:75-117`，这是整个同步引擎的心跳：

```
while (running) {
    等待 16.67ms（60fps 的帧间隔）;

    ① collectLocalInput()  → 采样本地键盘 → 存入 localInputBuffer
    ② gatherInputs()       → 从本地+远程缓冲区各取一条 InputCommand
    ③ predictInputs()      → 缺失的远程输入用 lastKnownInputs 预测
    ④ gameWorld.update()   → 确定性推进一帧
    ⑤ 检测游戏结束
    ⑥ checkAndRollback()   → 比对预测值和实际值，不一致就回滚

    currentFrame++;
}
```

### 步骤②：`gatherInputs()`（第 132-143 行）

```java
inputs.add(localInputBuffer.getInput(frameNumber));     // 本地一定有
for (InputBuffer remoteBuf : remoteInputBuffers.values()) {
    inputs.add(remoteBuf.getInput(frameNumber));        // 远程可能返回 null
}
```

网络延迟导致远程输入还没到 → `getInput()` 返回 `null` → 进入步骤③。

### 步骤③：`predictInputs()`（第 149-183 行）— 投机执行的核心

```java
for (InputCommand cmd : inputs) {
    if (cmd != null) {
        result.add(cmd);
        seenPlayers.add(cmd.playerId);
        if (!cmd.isEmpty()) {
            lastKnownInputs.put(cmd.playerId, cmd);  // 记录最近一次有效输入
        }
    }
}
// 远程玩家没出现在 seenPlayers 中 → 用上次有效操作预测
for (每个远程玩家) {
    if (没出现在 seenPlayers 中) {
        InputCommand predicted = lastKnownInputs.get(remotePlayerId);
        result.add(copyInput(predicted, 当前帧号, 该玩家ID));
    }
}
```

**关键细节**：`isEmpty()` 检查。空指令（站着不动）不更新 `lastKnownInputs`。因为"上一帧没按"不代表"下一帧也没按"——保留最后一次有效操作作为预测基准更合理。真实对战中操作密集，超过 95% 的帧都能正确预测。

## 4. 回滚机制

### `checkAndRollback()`（第 199-221 行）

```java
for (每个远程玩家) {
    // 从 confirmedFrame+1 开始逐帧检查，避免 UDP 乱序跳帧遗漏
    while (confirmedFrame < remoteBuf.getCurrentFrame()) {
        checkFrame = confirmedFrame + 1;
        confirmedInput = remoteBuf.getInput(checkFrame);  // 远程实际输入
        if (confirmedInput == null) break;                // 还没到，等

        predictedInput = lastKnownInputs.get(remoteId);    // 本地预测值

        if (!predictedInput.equals(confirmedInput)) {      // 预测错误！
            rollbackFrames = Math.min(currentFrame - confirmedFrame, 10);
            rollback(currentFrame - rollbackFrames);       // 回滚
            return;  // 回滚后当前检测上下文失效，直接返回
        }
        confirmedFrame++;  // 匹配成功，推进确认帧
    }
}
```

### `rollback()`（第 227-241 行）

```java
① gameWorld.rollbackTo(targetFrame);  // 恢复到最近的快照
② for (frame = targetFrame; frame < 之前的帧号; frame++) {
       inputs = gatherInputs(frame);       // 远程输入此时已到齐
       predicted = predictInputs(inputs, frame);
       gameWorld.update(predicted, frame); // 重新模拟
   }
```

### `GameWorld.rollbackTo()`（第 110-126 行）

```java
// 从快照列表里找 <= targetFrame 的最近一个快照
for (int i = snapshots.size() - 1; i >= 0; i--) {
    if (snapshots.get(i).getFrameNumber() <= frameNumber) {
        target = snapshots.get(i);
        break;
    }
}
target.restore(player1, player2);  // 恢复所有状态
snapshots.removeIf(s -> s.getFrameNumber() > frameNumber); // 清掉之后快照
```

### 回滚上限为什么是 10 帧？

10 帧 = 166ms。三层原因：
1. **网络层面**：超过 166ms 的预测错误说明网络已经烂到不该强行同步
2. **性能层面**：回滚不是免费的——重模拟消耗 CPU，每多回滚一帧约 +1ms
3. **体验层面**：10 帧以内的回滚肉眼不可察觉（<167ms）

## 5. GWT 版本的差异

`GwtFrameSyncManager.java` 和 `FrameSyncManager.java` 的**算法完全一样**。差异全部来自浏览器环境的限制：

| 差异点 | 桌面版 | GWT 版 |
|--------|--------|--------|
| 驱动方式 | 独立线程 `Thread` | `tick(deltaMs)` 从 `render()` 调用 |
| 时钟 | `System.currentTimeMillis()` | `accumulatedMs += deltaMs` |
| 并发容器 | `ConcurrentHashMap` | `HashMap`（单线程） |
| 帧追赶 | `Thread.sleep()` | delta 累积，最多追 5 帧 |
| 雪崩保护 | 无 | `accumulatedMs > 200ms` 时直接重置 |
| 锁 | `ReentrantReadWriteLock` | 无（单线程不需要锁） |

**为什么 GWT 不能开线程？** GWT 编译目标是 JavaScript，浏览器 JS 是单线程事件循环模型。`GwtFrameSyncManager` 本质上就是把"独立线程驱动"改写为"渲染循环驱动"——平台差异驱动的架构适配。

## 6. 面试追问 & 标准回答

### Q: 什么是"乐观"帧锁定？和悲观锁步有什么区别？

> **悲观锁步**：每帧等所有玩家输入到齐再推进，不预测、不回滚。延迟 = 所有人网络延迟之和。
> **乐观锁步**（Fyren）：不等，用上一帧输入预测当前帧。正确率 >95%。错误时回滚重算。延迟 = 单程网络延迟。
> "乐观"的意思是"我乐观地假设我的预测是对的"。

### Q: 回滚时屏幕会闪/跳吗？怎么处理？

> Fyren 不做显示层回滚——只回滚游戏逻辑状态。因为回滚通常在 1-3 帧内（~50ms），玩家肉眼无法察觉。GGPO 的做法类似：逻辑层回滚，渲染层平滑插值。这是"逻辑与表现的分离"。

### Q: 快照为什么是每 10 帧而不是每帧？

> 内存和性能的权衡。每帧快照 = 每秒 60 个快照，每个 40+ 字段 → 大量内存分配 + GC 压力。10 帧间隔意味着最坏情况回滚代价 = 从最近快照重算最多 9 帧 ≈ 150ms，完全可接受。

### Q: 如果网络断了 2 秒怎么办？

> `GwtFrameSyncManager` 有雪崩保护：`if (accumulatedMs > 200f) accumulatedMs = 0f`。断线重连后不会试图追赶 120 帧（会卡死），直接丢弃积压跳到当前状态。桌面板没有这个保护——这是已知局限，GWT 版已有应对。

### Q: 为什么输入按 playerId 排序？

> `GameWorld.update()` 第 59 行：`inputs.sort(Comparator.comparingInt(c -> c.playerId))`。两台机器各自独立排序，但排序依据是固定的 playerId → 结果永远一致 → 确定性保证。同一帧内 P1 和 P2 同时出招时的处理顺序是确定且一致的。

### Q: `lastKnownInputs` 为什么空指令不更新？

> 如果对手松开所有按键站着不动，`lastKnownInputs` 被空指令覆盖 → 下一帧预测值变成空指令。但如果对手下一帧突然出拳，预测错误就会触发回滚。保留最后一次有效操作作为预测基准，回滚率更低。这是实践中验证过的优化。
